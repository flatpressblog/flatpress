# Reverse proxy and public URL detection

FlatPress distinguishes the PHP backend connection from the public request seen by the browser. This is required on shared hosts, CDNs, reverse proxies and load balancers that terminate TLS and forward the request to PHP over HTTP.

## Public request context

`fp-includes/core/core.connection.php` centralizes scheme and port detection in `fp_public_request_context()`.

Direct origin signals remain authoritative for the public scheme when PHP itself receives HTTPS. The public port is evaluated separately so that a hosting stack which sets `HTTPS=on` while proxying to backend port 80 does not leak `:80` into browser-visible HTTPS URLs. Forwarded headers are accepted for runtime security decisions only when at least one of these conditions is met:

- the proxy address is explicitly trusted or is a private/loopback/reserved intermediary;
- multiple independent proxy signals corroborate HTTPS;
- the installation has persisted `general['trust_forwarded_scheme']` during an administrator-confirmed setup or configuration save.

A single public `X-Forwarded-Proto: https` is therefore not trusted automatically for runtime security decisions. Mixed values such as `https,http` are treated as ambiguous. During setup it may be used only as an administrator-visible candidate; that untrusted candidate is never allowed to trigger an HTTPS redirect before configuration has been saved.

## Setup and migration

Setup and Location Migration Mode may use one unambiguous forwarded scheme as a URL *proposal*. The proposal is not a runtime security decision. `SERVER_NAME` remains the default host source for first-time setup, while explicit migration may use the validated request host.

When an administrator confirms a URL whose public transport matches a forwarded candidate that actually contributed to the proposed scheme or port, FlatPress persists `general['trust_forwarded_scheme'] = true`. This allows TLS-terminating infrastructures that expose only `X-Forwarded-Proto` to work without a provider-specific patch.

If the installation later moves to a direct HTTPS origin or another host and the configuration is saved there, the trust flag is recalculated from the current request.

## Public port handling

`SERVER_PORT` is the backend port and must not automatically become the public port after TLS termination. When a trusted forwarded context is used:

- a valid, unambiguous `X-Forwarded-Port` is used when present;
- otherwise the scheme default is assumed (`443` for HTTPS, `80` for HTTP) and omitted from generated URLs.

This prevents URLs such as `https://example.org:80/` when a hosting frontend forwards public HTTPS to PHP over HTTP port 80. The same normalization applies when the hosting stack also sets `HTTPS=on`; coherent direct HTTPS on a genuine non-default port such as 8443 is preserved unless an accepted forwarded context explicitly supplies a different public port.

## Canonical URL consumers

Plugins should not independently inspect `SERVER_PORT` or `X-Forwarded-*` to reconstruct public URLs. `fp_current_public_url()` uses the central canonical FlatPress origin and raw request URI. SEO Meta Tag Info uses this helper for current-page URLs.

## PrettyURLs

PrettyURLs Auto mode is intentionally conservative. It selects Pretty only from a positive FlatPress rewrite signal, an IIS rewrite signal, or a real routed request that reached `index.php`. A generic `REDIRECT_URL` is not sufficient because shared hosting platforms may set it for unrelated redirects.

The Apache configuration generated by PrettyURLs sets `FLATPRESS_PRETTYURLS=1` through `mod_rewrite`; this is the positive signal used on subsequent requests. If rewrite capability cannot be proven, Auto falls back to HTTP Get. Explicit Pretty remains available for NGINX and other servers configured outside `.htaccess`.

The green checks in the PrettyURLs admin panel are capability indicators, not an indication of which mode Auto selected. The admin page performs authenticated same-origin browser probes because a normal `admin.php` request cannot reliably prove PATH_INFO or front-controller rewriting. PATH Info gets a check only when a probe suffix actually reaches `index.php` as `PATH_INFO`/`ORIG_PATH_INFO`; Pretty gets a check only when a clean path without `index.php` actually reaches the FlatPress front controller. Existing positive request-time evidence may show the check immediately. HTTP Get intentionally has no green capability check because it is the portable fallback and requires no optional server feature.

## Update check

The update checker does not bypass hosting-provider outbound-connection restrictions. It reports transport, HTTP status and transport error details so a blocked server-to-server connection can be distinguished from a FlatPress parsing problem.

## Regression tests

Run:

```text
php tests/connection_proxy_regression.ph_
php tests/prettyurls_auto_mode_regression.ph_
```

The tests cover TLS termination on backend port 80 (with `HTTPS` unset and with `HTTPS=on`), first-install redirect suppression, untrusted and persisted forwarded-scheme handling, ambiguous proxy headers, non-default ports, host validation, PrettyURLs false positives, real PATH_INFO/Pretty capability probes, and explicit NGINX-compatible Pretty mode.
